# 負荷テスト実行結果レポート

## 概要

DynamoDB のパーティションキー設計がスロットリングに与える影響を、Bad Table (PK=warehouseId, カーディナリティ 3) に対する書き込み負荷で検証した。

テスト環境:
- リージョン: us-west-2
- テーブル: kiro-roasters-inventory-bad
- データ量: 15,000 レコード（5,000 SKU × 3 倉庫）
- 倉庫分布: 東京 70% / 大阪 20% / 福岡 10%（ホットスポットシミュレーション）

---

## 実行結果サマリー

| # | テーブル | WCU | 設定時間 | 設定 req/s | 実処理時間 | 総リクエスト | 成功 | スロットル | スロットル率 | 備考 |
|---|---------|-----|---------|-----------|-----------|------------|------|-----------|-------------|------|
| 1 | bad | 100 | 60s | 50 | 71s | 3,000 | 3,000 | 0 | 0% | プロビジョン容量内（50 < 100 WCU） |
| 2 | bad | 100 | 60s | 50 | 69s | 3,000 | 3,000 | 0 | 0% | 同上（連続実行） |
| 3 | bad | 100 | 300s | 200 | 300s (timeout×3) | 7,000 | 3,820 | 3,180 | 45% | Lambda タイムアウト + ソケット枯渇 |
| 4 | bad | **5** | 60s | 50 | 103s | 3,000 | 2,203 | 797 | **27%** | WCU 大幅削減でスロットリング成功 |

## 詳細分析

### テスト 1-2: WCU 100, 50 req/s, 60 秒

**結果**: スロットリングなし

**原因**: 負荷がプロビジョン容量に達していない
- アイテムサイズは実測 205 バイト（3MB ÷ 15,000 件）。1KB 未満なので **1 書き込み = 1 WCU**
- したがって 50 req/s × 1 WCU/件 = 50 WCU/秒。プロビジョンは 100 WCU/秒 なので、容量の半分しか使っていない
- しかも実効レートは 42 req/s（3,000 / 71s）= 42 WCU/秒 なので、さらに余裕がある
- パーティション単位の上限 1,000 WCU/秒 にも遠く及ばない
- つまり「バーストキャパシティが助けた」という解釈は誤り。バーストはプロビジョン容量を超過したときに初めて出番があるもので、このテストはそもそもスロットルする条件（プロビジョン超過、またはパーティション上限超過）を満たしていない

**Lambda 実行ログ**:
- Start ハンドラー: 1,193 ms（非同期 Invoke + executions テーブル書き込み）
- Worker ハンドラー: 71,410 ms（設定 60 秒に対して +11 秒のオーバーヘッド）
  - 原因: Promise.all の完了待ち + executions テーブル更新の遅延

### テスト 3: WCU 100, 200 req/s, 300 秒

**結果**: 45% スロットリング（ただし Lambda 側の問題あり）

**Lambda 実行ログ**:
- Worker ハンドラー: 300,000 ms × 3 回（タイムアウト）
- `Status: timeout` が 3 回記録（Event 型 Invoke のリトライ）

**注意: この結果の数値は信頼できない**

- スロットル率 45%（3,180 / 7,000）と実効 23 req/s は両立しない。23 req/s = 23 WCU/秒 はプロビジョン 100 WCU/秒 の 1/4 でしかなく、この条件でスロットルが 45% 発生する説明がつかない
- 考えられる原因:
  - Event 型 Invoke のリトライにより 3 つのワーカーが同時に走り、DynamoDB に届いた実際の負荷が記録された値の 3 倍だった
  - タイムアウトで強制終了されたため、executions テーブルに書き戻された総リクエスト数自体が欠損している
- 結論: このテストは多重実行により正確な計測ができておらず、**スロットル率を根拠として扱うべきではない**

**発見された問題**:

1. **Lambda タイムアウト（300 秒）= テスト時間（300 秒）**
   - Worker の処理オーバーヘッドにより、300 秒のテストが 300 秒以内に完了しない
   - Lambda がタイムアウトすると Event 型 Invoke は最大 2 回リトライする
   - 結果: 3 回 × 300 秒 = 裏で約 15 分間実行が継続

2. **Node.js HTTP ソケット枯渇**
   ```
   @smithy/node-http-handler:WARN - socket usage at capacity=50 and 141 additional requests are enqueued
   ```
   - デフォルトソケット数: 50
   - 200 並列リクエストに対してソケットが不足
   - 実効レート: ~23 req/s（7,000 / 300s）= 設定 200 req/s の約 12%
   - **ただしソケット枯渇は要因の一つであり主因ではない**。後の検証で `maxSockets` を 500 に引き上げても実効 RPS は改善しなかった。真の主因はワーカーのクローズドループ構造にある（詳細は「負荷テスト基盤の既知の問題 → 根本原因: クローズドループ構造」を参照）

3. **executions テーブルの最終更新不整合**
   - タイムアウトで強制終了されたため、ステータスが RUNNING のまま残った
   - 画面上は「実行中」表示が続いた

### テスト 4: WCU 5, 50 req/s, 60 秒

**結果**: 27% スロットリング（797 / 3,000）

**CloudWatch メトリクス**:
- WriteThrottleEvents: 2,456 回（5 分間合計）
  - 21:15-21:20 UTC: 1,668 回
  - 21:20-21:25 UTC: 788 回
- ConsumedWriteCapacityUnits: 2,206（5 分間合計、テスト 4 実行時）

**Lambda 実行ログ**:
- Worker ハンドラー: 103,682 ms（設定 60 秒に対して +43 秒のオーバーヘッド）
- 原因: スロットリング発生時の DynamoDB レスポンス遅延 + Promise.all の待ち時間増加

**バーストキャパシティの枯渇過程**:
- バーストキャパシティ = 5 WCU × 300 秒 = 1,500
- 実測から逆算すると、成功 2,203 件 ÷ 103 秒 ≈ **21 WCU/秒**（アイテム 205 バイトなので 1 件 = 1 WCU）。プロビジョン 5 WCU/秒 の約 4 倍を持続できていた
- 超過分は 21 - 5 = 16 WCU/秒。バースト残高 1,500 に対して 1,500 ÷ 16 ≈ **91 秒** で枯渇する計算になる（30 秒ではない）
- ただしそれだと終盤の約 12 秒しかスロットルしないことになり、観測された 797 件のスロットルには届かない。この計算だけでは実測を完全に説明できない
- 観測値としての事実は **スロットル率 27%（797 / 3,000）** であり、「約 90% がスロットリング対象」という見積もりは根拠がないため採用しない
- なお DynamoDB のバーストは best effort で、背景処理（パーティション分割やインデックス更新など）にバースト分が消費されることがある。バースト残量を前提とした精密な予測は原理的に難しい

## 副次的発見: 出庫 API のスロットリング耐性

テスト 4 実行中に、別タブから在庫管理画面で出庫処理を手動実行した結果:

**結果**: 正常に処理完了（スロットリングエラーなし）

**原因**: AWS SDK v3 のデフォルトリトライ動作
- SDK は `ProvisionedThroughputExceededException` を受けると指数バックオフで自動リトライ（最大 3 回）
- 1 リクエストが 1 回スロットリングされても、数百ミリ秒後のリトライで成功する
- 負荷テスト Worker はリトライなしで即 throttleCount++ しているが、通常の Lambda はリトライ込みで成功する

**業務システムへの示唆**:
- 軽度のスロットリング: レイテンシ増加（リトライ遅延）だが処理は成功する
- 重度のスロットリング: リトライ上限超過 → ユーザーにエラーが見える
- 単発リクエストではスロットリングを「体感」しにくい

### レイテンシ比較: 通常時 vs 負荷テスト中

テスト 4（WCU 5, 50 req/s）実行中と、負荷なし通常時に同じ出庫処理（Bad Table）を手動で 3 回実行し、Lambda の実行時間を比較した。

**通常時（負荷なし、WCU 5）:**

| # | Duration | Init Duration | 備考 |
|---|----------|---------------|------|
| 1 | 922 ms | 372 ms | コールドスタート |
| 2 | 59 ms | - | ウォーム |
| 3 | 55 ms | - | ウォーム |

**テスト 4 実行中（WCU 5, スロットリング 27% 発生中）:**

| # | Duration | Init Duration | 備考 |
|---|----------|---------------|------|
| 1 | 941 ms | 381 ms | コールドスタート |
| 2 | 58 ms | - | ウォーム |
| 3 | 247 ms | - | ウォーム（Lambda Overhead 138ms） |

**X-Ray トレース確認結果:**
- 3 リクエストとも `has_throttle: false` — DynamoDB レベルでのスロットリングは未発生
- 247 ms の内訳: Lambda 実行 115 ms + ランタイム Overhead 138 ms（リトライではない）
- SDK 内部リトライの痕跡なし

**考察:**
- サンプル数 3 回では、負荷テスト中でも出庫 API への明確なレイテンシ影響は確認できなかった
- 単発リクエストが WCU 5 の「空き枠」にちょうどハマって成功した形
- DynamoDB のスロットリングは統計的制御であり、100% の拒否ではないため、低頻度のリクエストは通りやすい
- より明確な差を観測するには、負荷テスト中に出庫を連続 20〜30 回実行するスクリプトを回す必要がある

## 負荷テスト基盤の既知の問題

| 問題 | 影響 | 原因 | 対策案 |
|------|------|------|--------|
| Lambda タイムアウト 300s = テスト上限 300s | 300s テストが完了しない | Worker のオーバーヘッドで 300s を超過 | タイムアウトを 900s に引き上げ |
| Event 型 Invoke のリトライ | タイムアウト後に最大 3 回再実行 | Lambda の非同期 Invoke デフォルト動作 | `maximumRetryAttempts: 0` を設定 |
| ソケット枯渇（50 本上限） | 200 req/s が実効 ~50 req/s に低下 | Node.js HTTP Agent のデフォルト制限 | `maxSockets` 拡大は副次的。主因はクローズドループ構造（下記参照） |
| 実処理時間 > 設定時間 | 60s 設定で 103s かかる | クローズドループ構造 — 1 秒分の全リクエストの完了を待ってから次の秒に進むため、レイテンシがそのまま経過時間に加算される | 1 ワーカーの担当 RPS を下げて頭数を増やす（実測: 500→150 req/s + 4→14 ワーカーで改善） |
| ステータスが RUNNING のまま残る | UI に「実行中」が表示され続ける | タイムアウトで COMPLETED に更新できない | TTL or フロントエンドでタイムアウト検知 |

### 根本原因: クローズドループ構造

ワーカーのループは、1 秒分の全リクエストの完了を待ってから次の秒に進む構造になっている。

```ts
for (let sec = 0; sec < durationSeconds; sec++) {
  const start = Date.now();
  const promises = [];
  for (let i = 0; i < requestsPerSecond; i++) {
    promises.push(sendRequest());
  }
  await Promise.all(promises);          // 1 秒分の全完了を待つ
  const elapsed = Date.now() - start;
  if (elapsed < 1000) await sleep(1000 - elapsed);
}
```

このため実効 RPS は次の関係に支配される。

```
実効 RPS = 同時実行数 ÷ レイテンシ
```

宣言した RPS は上限としてしか働かず、レイテンシが伸びるほど RPS が落ちる**自己抑制構造**になっている。スロットルでレイテンシが伸びると負荷が自動的に下がるため、狙った負荷が DynamoDB に届かない。

実測での確認:
- Lambda の `maxSockets` を 500 に増やしても実効 500〜640 RPS で頭打ち
- EC2 でスレッドを 600 に増やしても同様に実効 500〜640 RPS で頭打ち
- 実際に効いた対策は **1 ワーカーの担当 RPS を下げて頭数を増やすこと**（500 → 150 req/s、4 → 14 ワーカー）と、Lambda メモリ増強（1024 → 2048MB）

## CloudWatch メトリクス観測値

### スロットル理由の切り分け

CloudWatch にはスロットルの**理由別メトリクス**が用意されている。これを使えば、容量不足なのかホットパーティションなのかを推測なしに切り分けられる。

| メトリクス | 意味 |
|-----------|------|
| `WriteProvisionedThroughputThrottleEvents` | テーブル全体のプロビジョン容量不足によるスロットル |
| `WriteKeyRangeThroughputThrottleEvents` | ホットパーティションによるスロットル（パーティション単位の 1,000 WCU/秒 超過） |

反省点: テスト 1〜5 ではこのメトリクスを使わず、合計値である `WriteThrottleEvents` のみを見ていた。そのため「容量不足によるスロットル」と「ホットスポットによるスロットル」を区別できず、テスト 5 の結果を「キー設計差が出なかった」と解釈してしまった。

今後の実験では、この 2 つのメトリクスを**必ず併せて確認する**。

| 2026-06-24 21:55 | 10,234 | テスト 3 リトライ分 |

## 結論

（テスト 1〜5 の範囲で言えることに限定した結論）

1. **WCU 100 / 50 req/s でスロットルしなかったのは、単にプロビジョン容量内だったため**。アイテム 205 バイト = 1 WCU なので 50 WCU/秒 の消費に対しプロビジョンは 100 WCU/秒。バーストの出番はなく、「バーストが吸収した」という説明は成立しない。

2. **スロットリングを確実に発生させるには**、WCU を大幅に下げてプロビジョン容量そのものを超過させる（テスト 4 の WCU 5）か、パーティション単位の 1,000 WCU/秒 を超える集中負荷を作る必要がある。両者は別の現象。

3. **バーストキャパシティとアダプティブキャパシティは、いずれもパーティション単位の上限（1,000 WCU/秒）を緩和できない**。AWS ドキュメントの記載どおり、burst capacity can't alleviate partition-level throttling であり、instant adaptive capacity can never cross the limit of 1,000 WCU per partition。
   - アダプティブキャパシティがやるのは「テーブルの余剰プロビジョンをホットパーティションに再配分する」ことであり、1,000 WCU の物理上限は超えられない
   - ホットキーの上限を実際に引き上げるのは **split-for-heat**（ソートキー範囲でのパーティション分割）という別の仕組み
   - バースト / アダプティブキャパシティ / split-for-heat の 3 つは分けて理解する必要がある

4. **負荷テスト基盤自体に改善が必要** — Lambda のタイムアウト、Event 型 Invoke のリトライ、そして最大の要因であるクローズドループ構造が実験結果の精度に影響している。テスト 3 と テスト 5 のレイテンシ値は計測系のノイズが支配的で、根拠として使えない。

5. **業務システムでの現実的なリスク** — SDK のデフォルトリトライにより単発リクエストではスロットリングは見えにくい。問題が顕在化するのは持続的な高負荷下で全リクエストがリトライ上限に達する状況。

6. **テスト 5 までの範囲では、小規模テーブル（WCU 5）でホットスポットを観測できる条件が整っていなかった**。パーティション単位のスロットルを観測するには、物理パーティションが複数存在し、かつテーブル容量に余裕がある状態を作る必要がある。テスト 5 の結果は「キー設計に差がない」ことの証明ではなく、「この条件では測定できない」ことを示している。

## テスト 5: オンライン影響テスト（WCU 5, 10 req/s, 10 秒）— Bad vs Good 比較

### テスト概要

バースト枯渇後に「オンライン影響テスト」機能を使い、Bad Table と Good Table で同一条件の連続出庫を実行。SDK リトライ無効（`maxAttempts: 1`）でスロットリングの生の影響を計測した。

テスト条件:
- リージョン: us-west-2
- 両テーブル WCU: **5**（RCU: 100）
- リクエスト/秒: 10
- 継続秒数: 10
- 倉庫: WH-TOKYO
- SDK リトライ: **無効**（maxAttempts: 1）

### 実行結果

| # | Table | Warehouse | RPS × Duration | Total | Success | Throttle | Throttle % | Avg ms | p50 ms | p95 ms | p99 ms |
|---|-------|-----------|---------------|-------|---------|----------|-----------|--------|--------|--------|--------|
| 1 | Bad | WH-TOKYO | 10 × 10s | 100 | 50 | 50 | **50.0%** | 201 | 138 | 660 | 1,020 |
| 2 | Good | WH-TOKYO | 10 × 10s | 100 | 46 | 54 | **54.0%** | 235 | 155 | 1,040 | 1,098 |

**重要: レイテンシ値は計測系のオーバーヘッドを含む**

Throttle 率（Bad 50% / Good 54%）は有効な観測値だが、**レイテンシ（Avg / p50 / p95 / p99）は DynamoDB の性能を表していない**。原因は `online-impact-test` Lambda 側の 2 つの欠陥。

1. **memorySize 未指定** — Lambda の既定 128MB（約 0.08 vCPU）で動いていた。SigV4 署名の HMAC 計算と TLS ハンドシェイクが CPU 待ちになる
2. **keepAlive 無効** — `new HttpsAgent({ maxSockets: 300 })` は Node の既定で `keepAlive=false` のため、毎リクエストで TCP + TLS ハンドシェイクをやり直していた

この 2 点のみを修正（memorySize 1024 + keepAlive: true）し、DynamoDB 側（WCU、キー設計、負荷条件）は一切変えずに再計測した結果:

| 指標 | 修正前 | 修正後 |
|------|--------|--------|
| avg | 599 ms | **19 ms** |
| p50 | 553 ms | **12 ms** |
| p95 | 802 ms | **78 ms** |

テスト 5 の avg 201ms / p95 660〜1,040ms も同じコードパスで計測されているため、**大半が計測ノイズ**である。レイテンシの絶対値を DynamoDB の性能として引用してはならない。

### 分析

**結果**: Bad Table と Good Table で差が出なかった。むしろ Good Table の方がわずかにスロットル率が高い。

**原因**: テーブル全体のキャパシティ不足

- 両テーブルとも WCU=5 → 物理パーティションは **1 つ** しか存在しない
- 物理パーティション分割の閾値は 1,000 WCU。WCU=5 では Bad/Good どちらもデータは同一物理パーティションに収まる
- パーティションキーの分散（3 vs 5,000）は、物理パーティションが複数存在して初めて意味を持つ
- WCU=5 に対して 10 req/s は単純にテーブルレベルでキャパシティ超過 → 設計の良し悪しに関係なくスロットリング発生

**学び**:
- ホットスポット問題は **物理パーティションが複数に分割される規模** でのみ顕在化する
- プロビジョンドモードでテーブル容量が不足している場合は、キー設計に関係なく **容量不足によるスロットルが先に発生する**。この状態ではキー設計の効果を測定できない
- ただし「キー設計差が影響しない」わけではない。テーブル容量に余裕がある状態では、パーティション単位のスロットルが容量不足とは独立に発生しうる
- 両者は CloudWatch の理由別メトリクス（`WriteProvisionedThroughputThrottleEvents` / `WriteKeyRangeThroughputThrottleEvents`）で区別できる
- テーブルレベルのキャパシティ不足と、パーティションレベルのホットスポットは別の問題

## テスト 6: 4 パターン比較 — キー設計 / GSI / 課金モードの影響

### テスト条件

- リージョン: us-west-2
- 負荷: 宣言 4,000 RPS × 120 秒（27 ワーカー × 149 req/s）
- 倉庫分布: 東京 80% / 大阪 10% / 福岡 10%
- seed: 各テーブル 15,000 レコード（5,000 SKU × 3 倉庫）、4 テーブル合計 60,000
- 負荷生成クライアントは `maxAttempts: 1`（SDK リトライ無効）

| badOnDemand | kiro-roasters-inventory-bad-ondemand | warehouseId / itemId | オンデマンド | PAY_PER_REQUEST | なし |

### 事前に修正した負荷生成側の不具合

**不具合 1: 並列 Scan によるワーカーの空転**

前回の対策として導入した並列 Scan（`Segment=workerId` / `TotalSegments=workerCount`）が、低カーディナリティ PK のテーブルで致命的に機能しなかった。

- 並列 Scan はパーティションキーのハッシュ空間でセグメントを分割する
- `bad` / `badOnDemand` は PK=warehouseId で値が 3 種類（WH-TOKYO / WH-OSAKA / WH-FUKUOKA）しかない
- 実測: `TotalSegments=27` で items が返ったのは segment 7 / 11 / 13 の 3 つだけ。残り 24 セグメントは 0 件
- 空セグメントを引いたワーカーは `items.length === 0` で即 return するため、27 ワーカーのうち 3 つしか負荷ループを回していなかった
- 結果: 総リクエスト 53,640 = 3 ワーカー × 149 req/s × 120 秒 という一致。実効 451 RPS（宣言 4,000 の 11%）

対策として SKU プール取得を start 側に移し、`ExclusiveStartKey` による順次 Scan で最大 2,000 件の distinct itemId を 1 回だけ取得し、全ワーカーに同じリストをペイロードで配る方式にした（2,000 件で約 30KB、非同期 Invoke の上限 256KB 内）。

修正後は 4 パターンすべてで**実効 4,034 RPS（宣言 4,000 の 101%）**を記録した。テスト 3〜5 の「クローズドループ構造により実効 RPS は宣言値の 50〜60% に留まる」という理解は、少なくとも 1 ワーカー 150 req/s の構成では成立しない。頭打ちの主因は SKU プール取得の欠陥だった。

**不具合 2: SDK 自動リトライによるスロットル過少計上**

負荷生成用の DynamoDB クライアントに `maxAttempts` を指定していなかったため、SDK 既定の standard リトライ（最大 3 回）が有効だった。スロットルされたリクエストが裏で再試行されるため `throttleCount` が実際より少なく計上され、かつクローズドループが再試行の待ち時間で押し下げられる。負荷生成専用に `maxAttempts: 1` のクライアントを分離した。進捗更新・完了マーク・SKU 取得は既定リトライのまま維持している。

### スロットル理由の内訳

全テーブルで `WriteProvisionedThroughputThrottleEvents` は **0**。スロットルの 100% が `WriteKeyRangeThroughputThrottleEvents` だった。WCU 10,000 のプロビジョン上限には一度も触れていない。テスト 1〜5 で区別できていなかった「容量不足」と「ホットパーティション」が、今回は完全に後者だけだったことになる。

bad の数値は理論値と一致する:

- 東京への要求 = 4,034 × 0.8 = 3,227 WCU/s、パーティション上限 1,000 WCU/s
- 大阪 + 福岡 = 807 WCU/s
- 処理可能な合計 = 1,000 + 807 = 1,807 WCU/s（実測 1,805/s）
- 溢れる分 = 3,227 − 1,000 = 2,227 WCU/s、全体の 55.2%（実測 54.8%）

### goodGsi の内訳 — GSI バックプレッシャー

ベーステーブルのスロットルは 0 で、GSI 側だけが詰まっていた。

| GSI | PK / SK | 消費 WCU ピーク | KeyRange スロットル |
|---|---|---|---|
| byWarehouse | warehouseId / itemId | 3,201/s | 53,803 |
| byLocation | warehouseId / location | 3,201/s | 44,910 |
| byUnitPrice | warehouseId / unitPrice | 3,201/s | 35,491 |

3 本すべて PK が `warehouseId` のため、ベーステーブルで解消したホットパーティションがインデックス側で再現している。ベーステーブルの消費 WCU が good の 3,995/s から 3,238/s に落ちているのが GSI バックプレッシャーの実測値。**ベーステーブルのキー設計を正しくしても、GSI の PK を間違えるとホットスポットは戻ってくる。**

### 計測系の注意点

- オンライン影響テストは API Gateway REST API 経由の同期呼び出しで、統合タイムアウトの上限が 29 秒。画面からは合計 25 秒（例: 10 秒 × 2 ラウンド）までしか実行できない。上表の 12 ラウンドは `lambda:Invoke` で直接呼び出して取得した
- 1 ラウンドの実測所要は約 9 秒。各ラウンド最後の 1 秒でスリープをスキップする実装のため
- 破棄したデータが 1 件ある。99 秒の同期 Invoke がクライアント側でリトライされ、オンライン影響テストが 2 本並走して 10 req/s のはずが 20 req/s になった。この実行は集計から除外した

- 実行間隔の差（bad は 4 分間隔、badOnDemand は 7 分間隔）
- 1 回 2 分という負荷継続時間が分割の判定に足りていない可能性
- オンデマンド固有の挙動（オンデマンドは過去のピークトラフィックに応じて事前にパーティションを増やす）

## 結論（テスト 6 を踏まえた追記）

1. **WCU 10,000 はホットパーティションから守ってくれない。** スロットルの 100% がパーティション単位（key-range）で、テーブル単位のプロビジョン容量は一度も上限に達していない。容量を積んでも設計が悪ければ 1 パーティション 1,000 WCU/s の壁で止まる。
2. **PK=itemId（分散設計）は 4,000 RPS を素通しした。** スロットル 0、消費 3,995 WCU/s。キー設計の効果が定量的に確認できた。
3. **GSI の PK を間違えるとホットスポットは戻る。** ベーステーブルは無傷でも GSI 側で key-range スロットルが発生し、ベーステーブルの書き込みスループットが 3,995 → 3,238 WCU/s に落ちた。
4. **「オンデマンドなら安全」は誤り。** 初回は bad と同じ 55% で詰まる。パーティション単位の 1,000 WCU/s 制限は課金モードに関係なく適用される。
5. **ただしオンデマンドは繰り返し負荷に適応した。** 3 回の実行で 1,800 → 2,797 → 4,005 WCU/s まで伸びてスロットルが消えた。同条件のプロビジョンドは 4 回とも 1,800 WCU/s のままだった。この差の機序は未確定。
6. **オンライン影響の測定にはサンプル数が必要。** 10 秒窓のスロットル率は 0〜98% に振れる。少数サンプルの「影響なし」は結論として使えない。
7. **負荷生成側の欠陥を疑うことが最優先。** テスト 3〜5 で「クローズドループ構造の限界」と結論づけた実効 RPS の頭打ちは、実際には SKU プール取得の実装バグだった。宣言値に対する実効値の乖離は、まず計測系を疑う。
