## 全体構想: 製造メーカーの社内システムクラウド化

この Kiro Roasters プロジェクトの背景にある大きなテーマは2つ。
検証・検討を進める中で、有用な知見が得られたものを記事化していく。

### 対象とする業務システム群

製造メーカーの社内システムは在庫管理だけではない。
営業・購買・製造・在庫・出荷・原価・会計・経営という複数の業務領域があり、
それぞれデータの性質（書き込み頻度、読み取りパターン、整合性要件）が異なる。
この性質の違いこそが「同期/非同期の境界」「DynamoDB/Aurora の使い分け」を考える素材になる。

| 業務領域 | 主な機能 | データの性質 | 書き込み負荷 | 読み取りの性質 |
|---------|---------|------------|------------|--------------|
| 営業（受注） | 受注登録、顧客管理、サブスク継続課金、見積 | トランザクション + マスタ | 中〜高（ECセール時にピーク） | 単品取得 + 売上集計 |
| 購買（仕入） | 生豆発注、入荷予定、取引先管理、発注残管理 | トランザクション | 低〜中（週次の発注業務） | 発注残照会、仕入履歴 |
| 製造（焙煎） | 焙煎計画、製造指図、焙煎実績、レシピ/BOM | トランザクション + 構成データ | 中（毎日の焙煎バッチ） | 計画照会、歩留まり集計 |
| 在庫管理 | 入出庫、在庫照会、棚卸し、ロット管理 | 高頻度更新 | 高（朝ピークに数千件） | 単品照会 + 全件棚卸し |
| 出荷・物流 | 出荷指示、ピッキング、配送追跡、倉庫間移動 | トランザクション | 高（朝の出荷ラッシュ） | 出荷ステータス照会 |
| 原価管理 | 仕入原価、製造原価、配賦計算、原価差異分析 | 集計バッチ | 低（月次締め） | 複数テーブルの JOIN・集計 |
| 会計・財務 | 売掛、買掛、仕訳、入金消込 | 厳密な整合性 | 中（日次仕訳） | 期間集計、財務レポート |
| 経営管理 | 経営ダッシュボード、KPI、需要予測 | 読み取り中心 | 低 | 大量データの集約・分析 |

**業務領域をまたぐデータの流れ（エンドツーエンド）:**

```
営業（受注）
   │ 受注確定イベント
   ▼
在庫（引当）──→ 在庫不足 ──→ 製造（焙煎計画）──→ 購買（生豆発注）
   │                              │                    │
   │ 出荷指示                      │ 焙煎実績            │ 入荷
   ▼                              ▼                    ▼
出荷・物流 ───────────────→ 在庫（入出庫）←──────────┘
   │                              │
   │ 出荷確定                      │ 入出庫イベント
   ▼                              ▼
会計（売上計上）            原価管理（製造原価・仕入原価）
   │                              │
   └──────────────┬───────────────┘
                  ▼
            経営管理（ダッシュボード・KPI）
```

この一連の流れの中で「どこを同期で繋ぎ、どこをイベントで疎結合にするか」が設計の肝になる。

### 従来型「バケツリレー」 vs データ中心イベント駆動

このプロジェクトで一番考察したいのが、業務システムの繋ぎ方そのものの変革。

従来の業務システムは、各システムが順番にデータを手渡ししていく**バケツリレー型**。
営業が受注を確定 → 夜間バッチで在庫システムへ連携 → 在庫が引当 → またバッチで製造システムへ…という具合に、
各システムが自前のDBを持ち、バッチ・ファイル連携・画面からの手入力でデータを受け渡す。

```
【従来：バケツリレー型】
営業DB → (夜間バッチ) → 在庫DB → (CSV連携) → 製造DB → (手入力) → 購買DB
  各システムが「現在値」を持ち、連携の遅延と不整合がつきまとう
  連携先が増えるたびに個別改修（点と点を線で繋ぐ N対N）

【データ中心：イベント駆動型】
                    ┌──→ 在庫（購読）
受注確定イベント ──┼──→ 製造（購読）
（単一の事実の流れ） ├──→ 会計（購読）
                    └──→ 経営（購読）
  発行側は購読側を知らない。関心のあるシステムが各自イベントを受け取る
```

| 観点 | 従来（バケツリレー） | データ中心イベント駆動 |
|------|-------------------|----------------------|
| データの受け渡し | バッチ／ファイル連携／手入力 | イベント（EventBridge / Streams / Kinesis） |
| 結合度 | 密結合（連携先を直接指定） | 疎結合（発行側は購読側を知らない） |
| データ鮮度 | 遅延あり（バッチ周期に依存） | ニアリアルタイム |
| 真実の源 | 各システムの現在値（重複・不整合が起きる） | イベントの履歴（単一の事実の流れ） |
| 履歴 | 上書きで消える | イベントとして残る（監査・再生が可能） |
| 拡張性 | 連携を追加するたびに改修 | 購読を1つ足すだけ |

**Kiro Roasters でこの違いを体感する例:**

- バケツリレー: 受注 → 夜間バッチで在庫引当 → 翌朝に欠品が判明 → 慌てて発注（後手に回る）
- イベント駆動: 受注確定イベントで即座に在庫引当 → 在庫不足イベント → 焙煎計画と発注提案が自動で走る（先手で動ける）

Phase 2 以降は、この「バケツリレーをどうイベント駆動へ置き換えるか」を、各業務システムを題材に1つずつ検証していく。

### 大テーマ① 完全サーバーレスの限界値

「どこまで同期で捌けるか」「どこから非同期に切り替えるべきか」の境界線を明らかにする。
また、DynamoDB だけでは対応できない領域を見極め、Aurora Serverless v2 との使い分けを判断する。

| 検討テーマ | 問い | Kiro Roasters での具体例（業務システム別） |
|-----------|------|------------------------|
| 同期処理の限界 | API GW → Lambda → DynamoDB の同期パスはどこで詰まるか | 【在庫】朝の出荷ラッシュで在庫照会が返ってこない／【営業】ECセール開始直後に受注登録が詰まる |
| 非同期への切り替え判断 | どの業務を SQS/EventBridge に逃がすべきか | 【出荷】出庫処理を非同期キューに入れたら照会は安定するか／【購買】発注確定後の入荷予定生成・取引先通知を非同期に |
| DB の使い分け | DynamoDB と Aurora Serverless v2 の境界線はどこか | 【在庫】高頻度入出庫 → DynamoDB／【原価】月次原価計算 → Aurora／【会計】仕訳・消込 → Aurora |
| リソースの使い分け | DynamoDB / SQS / Kinesis / Step Functions の選定基準 | 【製造】焙煎実績の連続イベント → Kinesis？／【出荷】出荷バッチのオーケストレーション → Step Functions？／【営業】受注 → SQS |
| Lambda の同時実行制御 | Provisioned Concurrency / Reserved Concurrency の効果 | 【在庫・出荷】朝のピークでコールドスタートが重なる／【会計】月末締めバッチが一斉起動して他業務を圧迫 |
| コスト vs パフォーマンス | オンデマンド vs プロビジョンドの損益分岐点 | 【出荷】朝だけピーク／【営業】ECは昼〜夕ピーク → 業務ごとに異なる山に Auto Scaling で間に合うか |

#### DynamoDB vs Aurora Serverless v2 の使い分け

製造業の業務システムでは RDB が必要になる場面が必ずある。
「完全サーバーレス」の文脈では Aurora Serverless v2 が選択肢になる。

**サーバーレス度合いの比較:**

| | DynamoDB | Aurora Serverless v2 | RDS（通常） |
|---|---|---|---|
| スケーリング | パーティション自動分割 | ACU 自動スケール（0.5〜128） | 手動（インスタンスサイズ変更） |
| ゼロスケール | オンデマンドなら実質ゼロ | 最小 0.5 ACU（完全ゼロ不可） | 不可（常時起動） |
| Lambda との相性 | ◎ HTTP API、コネクション不要 | △ RDS Proxy 併用推奨 | × コネクション枯渇リスク |
| 運用負荷 | ほぼゼロ | 低い（パッチ自動） | 高い |
| 課金モデル | RCU/WCU or リクエスト単位 | ACU × 時間 | インスタンス × 時間 |

**Kiro Roasters での使い分け想定:**

| 業務 | 特性 | 適切なDB |
|------|------|---------|
| 在庫の入出庫（リアルタイム） | 高頻度、単純な更新、低レイテンシ必須 | DynamoDB |
| 在庫照会（単品） | キーで1件取得、即座に返す | DynamoDB |
| 在庫一覧（倉庫別） | 1パーティション内の Query | DynamoDB (GSI) |
| 月次仕入原価計算 | 複数テーブル JOIN、集計関数 | Aurora Serverless v2 |
| 売上仕訳・会計処理 | トランザクション整合性、複雑なビジネスロジック | Aurora Serverless v2 |
| 経営ダッシュボード（集計） | 大量データの集約、期間指定の分析 | Aurora or Athena |
| ロットトレーサビリティ | 階層的な追跡クエリ | Aurora（再帰CTE）or DynamoDB（設計次第） |
| マスタ管理（商品、取引先） | 低頻度更新、複雑な検索条件 | Aurora Serverless v2 |

**「全部 DynamoDB」が破綻するポイント:**
- 複数エンティティを跨ぐ JOIN が必要になったとき
- 集計関数（SUM, AVG, GROUP BY）が頻繁に必要なとき
- アドホックなクエリ（事前にアクセスパターンを定義できない）が求められるとき
- 厳密な ACID トランザクションが複数アイテムに跨るとき

**検証で確認したいこと:**
- DynamoDB で無理に集計するコスト vs Aurora に逃がすコスト
- Lambda → Aurora Serverless v2 のコールドスタート + コネクション確立のレイテンシ
- RDS Proxy 経由のオーバーヘッド
- DynamoDB Streams → Lambda → Aurora のデータ同期パターンの実用性

### 大テーマ② データ指向型業務モデルへの変革

業務プロセスを「データフロー」として再設計し、イベント駆動型のシステムモデルを構築する。

| 検討テーマ | 問い | Kiro Roasters での具体例（業務システム別） |
|-----------|------|------------------------|
| データモデリング | 業務データのアクセスパターンをどう整理するか | 【在庫】在庫・入出庫・ロットの関係性／【製造】焙煎バッチとレシピ(BOM)／【営業】受注・顧客・サブスク |
| イベント駆動設計 | 状態変更をイベントとして捉え、後続処理を駆動する | 【営業→在庫→購買】受注確定 → 在庫引当 → 在庫不足 → 焙煎計画 → 生豆の自動発注提案 |
| CQRS | 書き込みモデルと読み取りモデルを分離する | 【在庫】入出庫(コマンド)と在庫照会(クエリ)／【営業】受注登録(コマンド)と売上ダッシュボード(クエリ) |
| イベントソーシング | 状態ではなくイベントの履歴を真のデータとする | 【在庫】在庫数を入出庫イベントの集計で導出／【会計】仕訳イベントの積み上げで残高を導出 |
| シングルテーブルデザイン | 関連エンティティを1テーブルに統合する | 【在庫】在庫・ロット・入出庫履歴／【製造】製造指図・工程実績／【購買】発注・入荷明細 |
| リアルタイム集計 | ストリーム処理で業務KPIをリアルタイムに可視化 | 【経営】在庫金額・回転率／【営業】当日売上の即時集計／【製造】焙煎進捗・歩留まり |

### 2つのテーマの交差点

```
①の限界値検証 ──→ 「ここから先は非同期」の線引き
                         │
                    「ここは DynamoDB / ここは Aurora」の線引き
                         │
                         ▼
②のデータモデル ──→ イベント駆動で非同期化する設計
                    DynamoDB + Aurora のポリグロット永続化
                         │
                         ▼
              技術的な判断材料が揃った状態
              （業務要件・組織判断と合わせて最終設計へ）
```

①で「同期の壁」「DynamoDB の壁」にぶつかる → ②の「イベント駆動」「DB使い分け」で解決する。
その先のゴールは、バケツリレー型の業務システム群を、イベントを軸にした疎結合なデータ中心モデルへ置き換えること。
ただし最終的なシステム設計は、技術検証だけでは決まらない（業務側の要件整理、結果整合性の許容判断、移行戦略、運用体制が別途必要）。

### 検討・検証ロードマップ

記事化するかは知見の有用性次第。検討・検証自体は順に進める。

```
Phase 1: 基礎検証（★今ここ｜題材: 在庫管理）
├── DynamoDB ホットスポット検証 → 同期の限界を体感する
├── キー設計パターンの比較 → データモデリングの第一歩
└── X-Ray / Contributor Insights の活用 → 可観測性の基盤

Phase 2: 同期/非同期の境界 & DB使い分け（題材: 出荷・製造・原価・会計）
├── 【出荷】出庫処理を SQS 経由に変更したときの在庫照会への影響
├── 【在庫】DynamoDB Streams で在庫変動をイベント化（バケツリレー→イベントの第一歩）
├── 【出荷】Step Functions で出荷バッチを非同期オーケストレーション
├── 【製造】焙煎実績の高頻度イベント: Kinesis vs SQS の捌き分け
├── 【原価・会計】Aurora Serverless v2 + RDS Proxy + Lambda のレイテンシ検証
├── 【原価】DynamoDB で無理な集計クエリ vs Aurora に逃がすパターン（月次原価計算）
└── 【会計】DynamoDB → Aurora のデータ同期（Streams → Lambda → Aurora）

Phase 3: データモデルの設計（題材: 製造・購買・営業）
├── 【在庫】シングルテーブルデザインの実践（在庫 + 入出庫 + ロット）
├── 【営業・原価】CQRS: コマンド(DynamoDB) / クエリ(Aurora) の分離（受注 vs 売上集計）
├── 【在庫・会計】イベントソーシング: イベント履歴から状態を導出（在庫数・勘定残高）
├── 【製造】製造指図・工程実績のモデリング（レシピ/BOM・歩留まり）
├── 【購買】発注〜入荷のステータス遷移モデル（発注残・入荷予定）
└── DynamoDB + Aurora のポリグロット永続化パターン

Phase 4: 業務システムとしての統合検証（題材: 経営・購買・営業・横断）
├── 【経営】リアルタイムダッシュボード（AppSync Subscriptions）
├── 【購買】欠品予測・自動発注（Bedrock + エージェント）
├── 【営業】受注フロントエンド（Amplify Gen2）
├── 【横断】バケツリレー型からイベント駆動型への移行シナリオ
└── コスト最適化・運用設計
```

## 記事化の判断基準

以下に該当する知見が得られたら記事にする:

- 実測データで「こうなる」と示せるもの（数字・グラフ・スクリーンショット）
- 既存記事にない切り口や深さがあるもの
- 自分自身が「これ先に知りたかった」と思えるもの
- 3軸（AWS / サーバーレス / Kiro）のうち2つ以上に該当するもの
