# 負荷テスト パート 2 — ホットスポット体感実験

## 目的

DynamoDB のホットスポット（パーティションキー設計の偏り）が、**オンラインユーザーの操作にリアルタイムで影響を与える**ことを実証する。

朝の出荷ラッシュ（バッチ的な大量書き込み）が走っている最中に、営業担当が在庫照会・出庫をしたら「エラーになる / 遅くなる」という業務シナリオを再現する。

---

## パート 1 からの学び

| テスト | 結果 | 原因 |
|--------|------|------|
| WCU=100 で 50 req/s | スロットルなし | バーストキャパシティで吸収 |
| WCU=5 で 50 req/s | スロットル 27% | テーブル全体のキャパ不足（設計差は関係なし） |
| WCU=5 で Bad vs Good 比較 | 両方 50% スロットル | 物理パーティション 1 つしかないため差が出ない |
| WCU=3000 で 1500 req/s | スロットルなし | 後から WCU を上げても物理パーティション分割が即座に起きない |

**結論**: 物理パーティションが複数に分割された状態を初期構築時に作る必要がある。

---

## 実験設計

### テーブル設定

WCU=10,000 でテーブルを**新規作成**することで、DynamoDB が初期配置時に物理パーティション約 10 個を割り当てることを狙う。

| テーブル | PK | WCU | RCU | 想定物理パーティション |
|---------|-----|------|------|---------------------|
| Bad Table | warehouseId (3 種) | 10,000 | 1,000 | ~10 |
| Good Table | itemId (5,000 種) | 10,000 | 1,000 | ~10 |

### 3 パターン比較

| # | 条件 | 期待結果 | 見せたいこと |
|---|------|---------|------------|
| ① | Bad Table + リトライ無効 | **エラー多発** | パーティションキー設計ミスの生の影響 |
| ② | Bad Table + リトライあり | **遅延するが成功**（一部エラー） | SDK リトライで隠れるが p95 レイテンシ悪化 |
| ③ | Good Table + リトライあり | **正常・高速** | 良い設計なら負荷テスト中でも影響なし |

### 負荷パラメータ

| パラメータ | 値 | 根拠 |
|-----------|-----|------|
| RPS | 1,500 | 東京 70% = 1,050 WCU → パーティション上限 1,000 超過 |
| 東京集中率 | 70% | |
| 大阪 | 20% | |
| 福岡 | 10% | |
| テスト時間 | 120 秒 | 手動操作の時間確保 + バーストキャパシティ枯渇 |

## 実行手順

### 事前準備

```bash
# 1. 既存 sandbox を削除
npx ampx sandbox delete

# 2. 再デプロイ（WCU=10,000 のテーブルが新規作成される）
npx ampx sandbox

# 3. 初期データ投入
curl -X POST ${API_URL}/seed

# 4. 開発サーバー起動
npm run dev
```

### ラウンド 1: Bad Table + リトライ無効

```
[負荷テストタブ]
  テーブル: Bad Table
  継続秒数: 120
  リクエスト/秒: 1500
  倉庫分布: 東京 0.7 / 大阪 0.2 / 福岡 0.1
  → 「負荷テスト開始」

[30 秒待ってから、在庫管理タブに切り替え]
  テーブル切替: Bad
  出庫処理:
    倉庫: WH-TOKYO
    商品ID: (一覧から適当に選ぶ)
    数量: 1
    ✅ リトライ無効にチェック
  → 「出庫」を 5〜10 回ポチポチ → エラーが出ることを確認

[負荷テストタブに戻る]
  オンライン影響テスト:
    テーブル: Bad Table
    倉庫: WH-TOKYO
    リクエスト/秒: 10
    継続秒数: 10
    SDKリトライ: 無効
  → 「実行」→ スロットル率の数値データを取得
```

### ラウンド 2: Bad Table + リトライあり

```
[負荷テストを再開始（または継続中なら OK）]

[在庫管理タブ]
  ☐ リトライ無効のチェックを外す
  → 同じ出庫を 5〜10 回ポチポチ → 成功するが遅い（Latency 表示を確認）

[オンライン影響テスト]
  SDKリトライ: 有効
  → 実行 → p95 レイテンシの悪化を数値で確認
```

### ラウンド 3: Good Table

```
[負荷テストタブ]
  テーブル: Good Table に切り替え
  同じパラメータ（1500 req/s, 120秒, 東京70%）
  → 「負荷テスト開始」

[30 秒待ってから、在庫管理タブ]
  テーブル切替: Good
  ✅ リトライ無効にチェック
  → 出庫を 5〜10 回ポチポチ → 正常に完了することを確認

[オンライン影響テスト]
  テーブル: Good Table
  SDKリトライ: 無効
  → 実行 → スロットルなし & 低レイテンシを確認
```

## 期待する結果

| 指標 | ① Bad + noRetry | ② Bad + retry | ③ Good + retry |
|------|----------------|--------------|----------------|
| 手動出庫 | ❌ エラー連発 | ✅ 成功（遅い） | ✅ 成功（速い） |
| Throttle 率 | 30〜70% | 0〜5%（リトライで吸収） | 0% |
| Avg Latency | 50〜100ms | 200〜500ms（リトライ遅延） | 30〜80ms |
| p95 Latency | 100〜200ms | 500〜1500ms | 50〜150ms |

## リスクと注意点

| リスク | 対策 |
|--------|------|
| WCU=10,000 でもパーティション分割が期待通りにならない | テーブルを新規作成（sandbox delete → 再作成）することで初期パーティション割り当てを狙う |
| split-for-heat でスロットルが自動解消される | DynamoDB の正常動作。「最初はエラー→自動回復」もストーリーとして記録 |
| バーストキャパシティで最初の 30 秒が吸収される | テスト開始から 30 秒以上待ってからオンライン操作を行う |
| Good Table の GSI も WH-TOKYO に偏る | GSI への書き込みは非同期のため、ベーステーブルの出庫には直接影響しない |
| API Gateway の 29 秒タイムアウト | オンライン影響テストは 10 req/s × 10 秒（100 リクエスト）に抑える |
